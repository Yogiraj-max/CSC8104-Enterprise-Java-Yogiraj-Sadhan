# CSC8104 Flight Booking Service

Flight booking service and TravelAgent for the CSC8104 Enterprise Software and Services coursework (Parts 1, 2 and 3), built on the
CSC8104 Quarkus quickstart. Allocated service type: **Flight**.

Interactive API documentation (Swagger UI) is served at **`/q/swagger-ui`** — locally
http://localhost:8080/q/swagger-ui, and at the same path on the OpenShift route.

## Running

```shell
# dev mode with live reload
./mvnw compile quarkus:dev -D"net.bytebuddy.experimental"

# run the REST Assured test suite
./mvnw clean test
```

## Package structure

| Package | Contents |
|---|---|
| `customer` | `Customer` entity, repository, validator, service and `CustomerRestService` (`/customers`) |
| `flight` | `Flight` entity, repository, validator, service and `FlightRestService` (`/flights`) |
| `booking` | `Booking` entity, repository, validator, service and `BookingRestService` (`/bookings`) |
| `guestbooking` | `GuestBooking` bean (not an entity) and `GuestBookingRestService` (`/guestbookings`) |
| `travelagent` | Part 3: REST clients for the Taxi and Hotel services, `TravelAgentBooking` entity, service and `TravelAgentRestService` (`/travelagent`) |
| `util` | Error handling shared by all REST services (`RestServiceException`, mapper, `ErrorMessage`) |

Each resource follows the quickstart layering: **RestService → Service → Validator / Repository → EntityManager (JPA) → H2**.

## Endpoints

| Method | URL | Purpose | Success | Errors |
|---|---|---|---|---|
| GET | `/customers` | List all customers | 200 | |
| GET | `/customers/{id}` | Get one customer | 200 | 404 |
| POST | `/customers` | Create a customer | 201 | 400 invalid, 409 email taken |
| DELETE | `/customers/{id}` | Delete customer **and their bookings** | 204 | 404 |
| GET | `/flights` | List all flights | 200 | |
| GET | `/flights/{id}` | Get one flight | 200 | 404 |
| POST | `/flights` | Create a flight | 201 | 400 invalid, 409 number taken |
| DELETE | `/flights/{id}` | Delete flight **and its bookings** | 204 | 404 |
| GET | `/bookings[?customerId=n]` | List all bookings, or one customer's | 200 | 404 unknown customer |
| GET | `/bookings/{id}` | Get one booking | 200 | 404 |
| POST | `/bookings` | Create a booking | 201 | 400 invalid / unknown ids, 409 flight already booked that date |
| DELETE | `/bookings/{id}` | Cancel a booking | 204 | 404 |
| POST | `/guestbookings` | Create customer + booking in one JTA transaction | 201 | 400, 409 (all rolled back) |

### Request bodies

```json
POST /customers
{ "name": "Jane Doe", "email": "jane@example.com", "phoneNumber": "07123456789" }

POST /flights
{ "flightNumber": "BA123", "departure": "NCL", "destination": "LHR" }

POST /bookings
{ "customerId": 1, "flightId": 1, "bookingDate": "2027-01-15" }

POST /guestbookings
{
  "customer": { "name": "Jane Doe", "email": "jane@example.com", "phoneNumber": "07123456789" },
  "booking":  { "flightId": 1, "bookingDate": "2027-01-15" }
}
```

Errors are returned as `{"error": "...", "reasons": {"field": "message"}}`.
Any `id` sent in a POST body is ignored — ids are always generated by the service.

### Validation rules

* Customer **name**: letters only (single spaces between words), 1–49 characters.
* Customer **email**: valid email address, unique.
* Customer **phoneNumber**: starts with `0`, exactly 11 digits.
* Flight **flightNumber**: exactly 5 letters/digits, unique.
* Flight **departure** / **destination**: exactly 3 upper-case letters; destination must differ from departure.
* Booking **bookingDate**: `yyyy-MM-dd`, strictly in the future. Only one booking per flight per date.

## Design notes

* **Relationships** – `Booking` has `@ManyToOne` links to `Customer` and `Flight`. Both `Customer.bookings` and
  `Flight.bookings` are `@OneToMany(mappedBy = ..., cascade = CascadeType.REMOVE, orphanRemoval = true)`, so deleting
  a customer or flight deletes its bookings automatically. The collections are `@JsonIgnore`d to avoid infinite
  JSON recursion.
* **Booking JSON** – clients send `customerId` / `flightId` (`@Transient` fields); `BookingService` resolves them
  into real entities. The full `customer` and `flight` objects are returned read-only in responses.
* **GuestBooking transaction** – `GuestBookingRestService` is deliberately *not* `@Transactional`. It injects the JTA
  `UserTransaction` and calls `begin()`, `commit()` and, on any failure, `rollback()` itself, so a customer is never
  saved without their booking. The tests prove this by checking the customer does not exist after a failed request.

## Part 3: TravelAgent

`/travelagent/bookings` books a **flight** (this service), a **taxi** and a **hotel** together, all or nothing:

| Part | Service | Owner |
|---|---|---|
| Taxi | `https://ess-coursework-parthrb-dev-dev.apps.rm2.thpm.p1.openshiftapps.com` | Parth Bhawar |
| Hotel | `https://csc-8104-sadit-indramangala-saditpond-dev.apps.rm3.7wse.p1.openshiftapps.com` | Sadit Indramangala |

| Method | URL | Purpose | Success | Errors |
|---|---|---|---|---|
| GET | `/travelagent/bookings[?customerId=n]` | List aggregate bookings | 200 | 404 unknown customer |
| GET | `/travelagent/bookings/{id}` | Get one | 200 | 404 |
| POST | `/travelagent/bookings` | Book taxi, hotel and flight | 201 | 400, 409, 502 (earlier parts cancelled) |
| DELETE | `/travelagent/bookings/{id}` | Cancel all three parts | 204 | 404, 502 (kept, can retry) |
| GET / POST | `/travelagent/taxis`, `/travelagent/hotels` | See or add taxis/hotels in the colleagues' services | 200 / 201 | 400, 409, 502 |

```json
POST /travelagent/bookings
{ "customerId": 1, "flightId": 1, "taxiId": 1, "hotelId": 1, "bookingDate": "2027-01-15" }
```
`customerId` and `flightId` are ids in this service; `taxiId` and `hotelId` are ids in the colleagues' services.

**How "all or nothing" works.** The steps run in order: (1) taxi, (2) hotel, (3) flight. The flight booking and the
`TravelAgentBooking` record are saved in one manually demarcated JTA transaction. The remote services cannot join that
transaction, so if any step fails the steps that already succeeded are undone by calling each service's cancel endpoint
(compensating actions). The error's `compensation` reason says what was undone.

**Demo of the required scenario (first two succeed, third fails):** book flight X on date D normally with `POST /bookings`,
then `POST /travelagent/bookings` for flight X on date D. The taxi and hotel are booked, the flight fails with 409
because it is already booked, and the taxi and hotel bookings are cancelled.

**Design notes.**
* All remote bookings are made by one "travel agent" customer in each colleague's service
  (`travelagent.customer.*` in `application.properties`). It is looked up by email before each booking and re-created if
  the colleague's in-memory database has been reset.
* The local flight `Booking` is linked to its `TravelAgentBooking` with `@OneToOne`; only the remote booking ids are
  stored. Deleting a customer or flight cascades to its travel agent bookings (remote bookings are not cancelled in that case).
* Cancelling treats a remote 404 as "already cancelled", so a failed cancel can safely be retried.
* The tests replace the Taxi and Hotel services with fakes (`QuarkusMock`), so they can force a failure at any step and
  do not depend on colleagues' services being up.

## Database

The service uses an in-memory H2 database (`jdbc:h2:mem:default;DB_CLOSE_DELAY=-1`), as the coursework requires
for OpenShift deployment. The H2 TCP server from the quickstart has been removed, so DBeaver cannot connect.
All data is lost whenever the application restarts or is redeployed.

## CI/CD

`.github/workflows/deploy-openshift.yml` is a GitHub Actions pipeline that runs on every push to `main`:

1. **Build and run tests** – runs the REST Assured test suite with `./mvnw clean test`.
2. **Deploy to OpenShift** – only if the tests pass: starts an S2I build of the pushed commit on OpenShift,
   then rolls out a new Knative revision so the new image goes live.

It uses two repository secrets, `OPENSHIFT_SERVER` and `OPENSHIFT_TOKEN` (a `github-actions` service account token).
A failing test stops the deploy, so broken code never reaches the live service.
